scenario:
  id: circleci_queue_db_lock_webhook_surge
  title: Webhook surge locks scheduler DB, stalling build queue and triggering emergency mitigations

  states: {n: normal, f: failure}

  summary: |
    The platform normally ingests GitHub webhooks, enqueues builds into a DB-backed scheduler queue, and continuously dequeues builds onto builders.
    During the modeled pre-incident window, GitHub push hook delivery is effectively absent while the platform remains otherwise healthy.
    When hook delivery resumes as a sustained surge, DB write pressure climbs quickly and then nonlinearly tips the shared DB into lock contention, collapsing dequeue throughput and stalling the build queue.
    Operators attempt LB throttling and a DB stepdown, then mitigate by disabling auto re-enqueue, reducing builder activity, live patching hot queries, and draining queues; the scenario ends while the system is still degraded and draining.

  trigger_desc: |
    GitHub webhook delivery returns after an upstream interruption and comes back as a sustained high-rate surge that is several multiples of normal peak, flooding the build enqueue path.

  time:
    total_minutes: 50
    phases:
      n: {start_min: 0, end_min: 25}
      f: {start_min: 25, end_min: 50}

  phases:
    n:
      desc: |
        Customer API traffic and a small amount of background scheduling operate normally.
        GitHub push hook deliveries are largely absent (a known external issue), so new build enqueues are near-zero while the service remains up.
        DB pool stats show low waiting/lock counts; slow query and statement timeout logging is effectively absent.
      flows: [customer_api_ok, scheduler_dequeue_ok]
      manifestation:
        - postgres_db.pool_stats
        - scheduler_service.queue_stats
        - api_service.api_req_ok
        - scheduler_service.dequeue_ok

    f:
      desc: |
        Failure begins when webhook delivery resumes as a sustained surge, increasing enqueue write pressure on the shared database.
        For a short period the system appears to cope (enqueues and dequeues still succeed), but the additional write load sets up a non-linear DB degradation.
        The database then becomes lock/contention bound: timeouts and slow queries appear and scheduler dequeue success collapses while queues grow.
        Mitigation attempts (LB throttling, DB stepdown) are followed by disabling auto re-enqueue, reducing builders, live patching hot queries, and draining queues.

      events:

          why: |
            The upstream GitHub interruption ends and buffered/renewed webhook delivery returns at a higher sustained rate than typical.
            This change is directly observable via increased webhook-related request logs before DB contention becomes dominant.
          flows:

          event: |
            The shared DB becomes lock/contention bound; query latency jumps, lock-wait alarms begin, and scheduler dequeue success collapses while the queue grows quickly.
          why: |
            High-rate build insertions and associated state writes amplify DB contention; once lock waits rise, throughput falls nonlinearly and timeouts appear across clients.
            This is directly observable in DB lock/timeouts/slow-query logs and in scheduler dequeue timeout logs; the specific root mechanism (lock contention) is inferred from correlated lock-wait signals.
          flows:
            - github_webhook_enqueue_ok
            - github_webhook_enqueue_timeout
            - scheduler_dequeue_timeout
            - customer_api_ok
            - customer_api_backend_500
          rate_multipliers:

          why: |
            Reducing capacity/limits at the LB is a fast lever to stop new builds from joining the queue, but webhook traffic dominates request volume and consumes the constrained inflight budget.
            This is directly observable as LB access logs with 503 and a throttling configuration-change marker.
          flows:

            The LB throttling is rolled back to restore customer access, and a DB stepdown/promote-secondary is initiated to try to flush queued operations and regain control.
          why: |
            The rollback is observable via a rapid reduction of LB-level 503s and an explicit rollback marker.
            The DB stepdown is an operational action; its effectiveness is only partially observable via subsequent DB pressure signals and queue behavior.
          flows:
            - customer_api_ok

        - order: 5

          component: ops_repl
          event: |
            The stepdown does not relieve load and re-enqueueing is amplifying DB writes, so operators disable auto re-enqueue, terminate builders to reduce activity, and live-patch hot queries.
            As part of triage, slow-query inspection becomes a focus, and slow-query logging becomes more prominent even as statement timeouts begin to drop.
          why: |
            Automatic re-enqueue turns infrastructure/stepdown failures into additional queue writes, sustaining the overload.
            Disabling re-enqueue and reducing builders lowers the volume of state updates, which can reduce timeouts; however, remaining inefficient queries still run slowly under large queue sizes and become more visible when the team actively collects slow-query evidence.
            The actions are directly observable via ops one-shot markers; timeouts decreasing and slow-query lines increasing are directly observable in DB logs.
          flows:
            - scheduler_dequeue_timeout
            - github_webhook_enqueue_timeout
            - customer_api_backend_500
          rate_multipliers:
            scheduler_service.reenqueue_build: 0.0
            builder_fleet.heartbeat: 0.3
            postgres_db.query_timeout: 0.7
            postgres_db.slow_query: 2.0
            github_webhook_enqueue_ok: 0.5
            github_webhook_enqueue_timeout: 0.7

            scheduler_dequeue_timeout: 0.8

              hosts: [ops1]

            - postgres_db.slow_query

          event: |
            With DB pressure partially reduced, operators start queue-drain scripts for the usage and run queues; progress logging begins and dequeue success becomes slightly more frequent, but the platform remains degraded.
          why: |
            Purging queued state requires DB reads/writes, so draining is only possible once contention is reduced enough for administrative scripts to make progress.
            This is directly observable via drain script start markers and periodic drain progress logs; improved dequeueing is inferred from a higher rate of scheduler dequeue success logs.
          flows:

          desc: |
            DB disruption (timeouts/failover) causes build attempts to fail, and automatic re-enqueue writes more queue state back into the same contended DB.
            The additional writes further increase lock contention and slow query execution, prolonging the stall until re-enqueue is disabled and load is forcibly reduced.

      flows:
        - github_webhook_enqueue_ok
