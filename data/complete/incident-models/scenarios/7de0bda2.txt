scenario:
  id: tiered_cache_tracing_headers_530
  title: Buggy tiered-cache tracing clears control headers causing intermittent 530s

  states: {n: normal, f: failure}

  summary: |
    The CDN normally serves most assets from local edge cache, using Tiered Cache to consult an upper tier on misses.
    A canary release on upper-tier POPs adds tracing instrumentation that clears internal control headers.
    When tiered requests reach an affected upper tier, required host context is missing, internal DNS lookups are made with an empty qname, and the edge returns HTTP 530.
    Impact grows as rollout reaches more/larger upper tiers, then begins to decline after a partial rollback, but the scenario ends before full recovery.

  trigger_desc: |
    A software release is started on upper-tier cache POPs enabling an opentracing wrapper that clears routing control headers needed for tiered-cache internal traffic.

  time:
    total_minutes: 50
    phases:
      n: {start_min: 0, end_min: 20}
      f: {start_min: 20, end_min: 50}

  phases:
    n:
      desc: |
        Edge POPs serve the majority of requests from local cache with low latency.
        For a smaller fraction of cache misses with Tiered Cache enabled, the edge queries an upper-tier POP,
        which either serves from its cache or resolves origin hostnames via internal DNS and fetches from origin.
        530 rates are near-zero and no incident/alert activity is present.
      flows: [client_asset_local_cache_hit, client_asset_tiered_upper_cache_hit, client_asset_tiered_upper_miss_origin_ok]
      manifestation: [edge_cache.access_hit_local, upper_tier_cache.upper_served_cache, internal_dns.dns_resolve_ok, observability.sli_530_sample]

    f:
      desc: |
        After the upper-tier release starts, some tiered requests arriving at affected upper-tier POPs lose required host context
        because control headers are cleared by the tracing wrapper. Upper tiers then cannot determine the origin hostname to resolve,
        internal DNS logs empty-qname SERVFAILs, and the edge returns 530 to clients.
        As rollout expands, the fraction of tiered requests hitting buggy upper tiers rises, causing a sharp increase in 530s and alerting activity.
        A partial rollback confirms the cause and reduces errors, but some upper tiers remain on the bad build by the end of this scenario.

      events:
        - order: 1
          at_min: 20
          component: upper_tier_cache
          event: |
            Canary deploy of the upper-tier cache build with tracing wrapper begins; low-rate tiered requests start failing with 530 when they hit the affected upper tier.
          why: |
            The tracing wrapper clears internal control headers before tiered-cache routing reads them; some internal tiered requests then arrive without hostname context.
            The deploy start is directly observable via a deploy log; the header-clearing side effect is inferred from missing control context and DNS empty-qname errors.
          flows: [client_asset_tiered_dns_error_530]
          rate_multipliers: {}
          latency_multipliers: {}
          one_shots:
            - ref: upper_tier_cache.release_started
              count: 1
              hosts: [atl1]
            - ref: internal_dns.dns_release_started
              count: 1
              hosts: [dns1]
          manifestation: [upper_tier_cache.release_started, upper_tier_cache.upper_recv_missing, internal_dns.dns_err_empty_qname, edge_cache.access_tiered_530]

        - order: 2
          at_min: 28
          component: observability
          event: |
            Rollout reaches more upper-tier traffic paths; customer-reported 5xx and SLI sampling activity increase as 530s become more noticeable.
          why: |
            As more tiered requests traverse upper tiers running the new build, the probability of missing control context increases, creating more empty-qname DNS errors and 530s.
            Alerts are directly observable in alerting logs, while exact rollout coverage is only partially observable from request outcomes.
          flows: [client_asset_tiered_dns_error_530]
          rate_multipliers:
            client_asset_tiered_dns_error_530: 3.0
            client_asset_tiered_upper_cache_hit: 0.9

        - order: 3
          at_min: 31
          component: edge_cache
          event: |
            A small edge POP is removed from tiered routing during investigation, slightly reducing 530 volume but not eliminating the symptom.
          why: |
            Draining one POP reduces the share of tiered requests reaching affected upper tiers, but the buggy build remains active elsewhere.
            The routing action is directly observable; the limited effect indicates the issue is not isolated to a single POP.
          flows: [client_asset_tiered_dns_error_530]
          rate_multipliers:
            client_asset_tiered_dns_error_530: 2.5
            client_asset_tiered_upper_cache_hit: 0.92
            client_asset_tiered_upper_miss_origin_ok: 0.92

          component: upper_tier_cache
          event: |
            An accelerated rollback is initiated across upper tiers, further reducing 530s but not completing before the scenario ends.
          why: |
            As more upper tiers revert, fewer tiered requests encounter the header-clearing behavior; however, some affected capacity remains.
            The action is directly observable; partial improvement is visible in reduced error-flow rate and continued DNS empty-qname errors.
          flows: [client_asset_tiered_dns_error_530]

            client_asset_tiered_dns_error_530: 2.0

      steady:

          condition: |
            Some upper-tier POPs remain on the tracing-wrapped build that clears tiered-cache control headers, intermittently stripping hostname context from internal tiered requests.
          user_impact: |
            A subset of tiered-cache-eligible requests fail with HTTP 530 (DNS error), while local-cache-hit traffic remains unaffected.
          manifestation: [upper_tier_cache.upper_no_host_error, internal_dns.dns_err_empty_qname, edge_cache.access_tiered_530]

      feedback_loops:

          desc: |

          desc: |
            Upper-tier POPs serve many lower-tier POPs; once large upper tiers receive the buggy build, a small code change produces a disproportionate increase in client-visible 530s.
