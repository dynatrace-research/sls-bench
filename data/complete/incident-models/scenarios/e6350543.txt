scenario:
  id: incident_2025_02_19_maps_tls_san
  title: Low-volume 502s from ATS due to missing maps.wikimedia.org SAN on Kubernetes Kartotherian cert

  states: {n: normal, f: failure}

  summary: |
    Maps tile traffic is served by ATS, which forwards origin requests through an L4 LVS service to Kartotherian origins.
    During a traffic-shift step, Kubernetes workers were pooled back into the LVS service even though their TLS certificate
    did not include the maps.wikimedia.org SAN. ATS used maps.wikimedia.org as SNI and rejected the certificate, producing
    a small but persistent stream of 502s visible in the Webrequest 50X dashboard, until operators depooled the Kubernetes workers.

  trigger_desc: |
    An operator pools Kubernetes Kartotherian backends into the LVS service (after a previous depool), unintentionally
    routing a small fraction of ATS origin connections to backends whose TLS certificate does not validate for maps.wikimedia.org.

  time:
    total_minutes: 50
    phases:
      n: {start_min: 0, end_min: 20}
      f: {start_min: 20, end_min: 50}

  phases:
    n:
      desc: |
        ATS forwards origin requests for map tiles normally. Requests are proxied through LVS to the bare-metal Kartotherian
        origins and return 200 responses. The Webrequest 5xx dashboard metric stays near zero, and the LVS pool snapshots
        show Kubernetes backends not in use.
      flows: [tile_request_ok]
      manifestation:
        - edge_ats.webrequest_ok
        - edge_ats.conn_summary_ok
        - lvs_kart.pool_status

        TLS verification when using maps.wikimedia.org as SNI because the certificate is missing that SAN. Only the subset of
        origin requests routed to those workers fails, so the 502 stream is subtle and does not trigger an immediate alarm.
        Operators later consult the 5xx dashboard and depool Kubernetes workers, eliminating user-facing errors but leaving Kubernetes
        capacity unusable until the certificate is fixed (outside this scenario window).

      events:

          why: |
            LVS only validates TCP reachability, so the Kubernetes backends appear usable. ATS performs TLS verification using
            the request Host as SNI, and the Kubernetes certificate lacks maps.wikimedia.org in its SANs, causing hostname
            mismatch and origin handshake failures (directly observable via ATS TLS-failure logs and webrequest 502s).

          why: |
            Removing Kubernetes backends eliminates ATS attempts to connect to the misconfigured certificate endpoints, so the
            TLS handshake failure path is no longer exercised by user traffic. This is directly observable as a sharp drop of
            ATS 502 webrequests and a return of dashboard/edge origin summaries to near-zero 5xx.
          flows: [tile_request_ok]
