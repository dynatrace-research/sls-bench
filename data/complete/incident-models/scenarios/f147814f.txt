scenario:
  id: browserstack_shellshock_legacy_host_2014
  title: Legacy prototype Shellshock compromise leads to AWS credential abuse, DB lock alerts, and service takedown

  states: {n: normal, f: failure}

  summary: |
    The service normally handles user web traffic via a frontend backed by an RDS database, while production servers block Shellshock probes.
    An attacker exploits an unpatched, inactive legacy prototype host to obtain embedded AWS keys and perform AWS control-plane actions.
    The attacker mounts a backup-derived configuration path to access the database and begins a bulk copy that locks/contends on a key table, triggering lock-wait alerts and user-facing slowness/errors.
    Operators block the attacker and take the service into maintenance mode while rotating keys, causing a sustained outage at the end of the scenario.

  trigger_desc: |
    A Shellshock exploit is successfully executed against an old prototype EC2 host that was left running and unpatched, exposing embedded AWS credentials.

  time:
    total_minutes: 34
    phases:
      n: {start_min: 0, end_min: 17}
      f: {start_min: 17, end_min: 34}

  phases:
    n:
      desc: |
        Users browse and run sessions through the public web frontend with typical latencies.
        Monitoring samples DB lock-wait metrics at a low baseline and the DB emits routine checkpoint logs.
        Production web servers occasionally log blocked Shellshock probes, indicating patching at the public edge.
      flows: [user_dashboard_ok, shellshock_probe_prod]
      manifestation:
        - web_frontend.http_resp_ok
        - web_frontend.web_health_ok
        - monitoring.metric_db_lockwait
        - web_frontend.shellshock_block

    f:
      desc: |
        The incident begins with successful Shellshock exploitation of an inactive legacy prototype host.
        Using embedded AWS credentials, the attacker performs AWS actions recorded in CloudTrail, later gaining DB access and initiating a bulk copy.
        The bulk copy and related contention cause lock waits and slow queries, degrading user request latency and causing 500 errors, which triggers monitoring alerts.
        Operators then revoke the attacker’s DB ingress, terminate the attacker instance, rotate keys, and enable maintenance mode, leaving the service unavailable through the end.

      events:
