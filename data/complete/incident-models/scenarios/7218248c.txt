scenario:
  id: travis_ci_db_truncate_20180313
  title: Production PostgreSQL tables truncated; empty-data window creates new users; restore leads to token/user mismatch

  states: {n: normal, f: failure}

  summary: |
    The system normally authenticates users, renders dashboards, and runs CI builds by persisting metadata in PostgreSQL
    and dispatching jobs via Redis to workers. The incident is triggered when a TRUNCATE statement against the production
    PostgreSQL database executes, emptying application tables while sequences continue. For a short period the API and web app
    continue running against the effectively empty dataset, creating new user records and showing blank profiles; later applications
    are taken offline for restore. After restore, some JWTs correspond to post-truncate user IDs that no longer match restored data,
    causing users to be forced to log out (and potentially perceive wrong-account symptoms) while build backlogs and missing cron triggers persist.

  trigger_desc: |
    A developer accidentally runs an automated test suite in a shell session with DATABASE_URL still pointing at the
    production PostgreSQL primary (with write access). The test tooling (e.g., database-cleaning helper) issues a TRUNCATE
    of application tables. The statement is blocked for several minutes by locks, then completes and truncates (empties) the production
    dataset before responders fully take user-facing applications offline.

      desc: |

        JWTs, and the web_app renders dashboards by fetching profile and repository data from postgres_primary. GitHub webhooks
        are received by the API, metadata is written to postgres_primary, and jobs are enqueued into job_queue for worker_pool
        to execute. Separately, build_scheduler periodically scans for cron-enabled repositories and enqueues scheduled builds.
        github_syncer runs regular sync cycles against github_api and upserts users/org memberships into postgres_primary.
        Operationally, background heartbeats and queue depth logs provide a stable baseline.
      flows:

      desc: |
        Failure begins when postgres_primary executes a TRUNCATE that empties application tables. For the first part of the failure phase,
        the API and web app continue operating against a mostly-empty dataset: dashboard loads run queries successfully but receive empty
        results, and the application responds by showing blank profiles. Login and GitHub sync code paths interpret missing user rows as new
        users and create fresh user records using sequences that continue from their pre-TRUNCATE values.
        Some write paths that depend on other rows being present (e.g., creating build records referencing repos/users) fail due to constraint
        violations or application-level “missing record” behavior.
        Incident response then intentionally takes applications offline to stop further mutations while postgres_primary is restored from a snapshot.
        During the offline window, edge_router returns 503s for most requests, and restore progress becomes visible via postgres_primary.restore_progress.
        Once the restore completes and services return, clients that obtained tokens during the empty-data window present JWTs whose subjects no longer
        correspond to the restored user mapping, causing api_service.jwt_user_mismatch and web_app.forced_logout. Build processing resumes but remains
        degraded due to backlog, and scheduled builds are missed because build_scheduler is not restarted promptly, producing persistent missed-schedule
        warnings and “scheduler not running” signals.

          why: |

            it can complete a scan but find zero candidates because the repo/schedule tables are empty, observable as build_scheduler.cron_scan_complete with
            candidates/enqueued near zero. Some write paths that reference other tables (repos/builds) can violate foreign keys or uniqueness assumptions,
            observable as postgres_primary.sql_error (SQLSTATE 23503/23505) paired with api_service.enqueue_failed_db in webhook_build_trigger_db_error.
