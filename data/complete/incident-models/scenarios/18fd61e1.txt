scenario:
  id: eu_gateway_restart_kazoo_zk_buffer_incident
  title: Gateways restarted while orchestrator unstable; ZooKeeper session churn and strace EPIPE during startup burst, then ZooKeeper max-buffer rejection; recovery after buffer increase

  states: {n: normal, f: failure}

  summary: |
    In normal operation, gateways route user HTTP traffic to application runtimes using a routing table refreshed from the orchestrator.
    During a maintenance upgrade, gateways were restarted while the orchestrator was not fully started, clearing in-memory routes and preventing refresh, so websites returned 503 no_route.
    The orchestrator showed repeated ZooKeeper session churn and slow lock acquisition; operators used strace to discover frequent EPIPE errors during the startup burst (a Kazoo-related scaling issue), and applied a hotfix to throttle client-side load.
    After the hotfix, a separate issue surfaced: ZooKeeper consistently rejected an oversized node/packet due to jute.maxbuffer; increasing the ZooKeeper max buffer and restarting ZooKeeper restored route serving and most website traffic.

  trigger_desc: |
    Maintenance procedure restarts/upgrades the gateway cluster before verifying the orchestrator is fully started and able to serve routing snapshots.

  time:
    total_minutes: 50
    phases:
      n: {start_min: 0, end_min: 20}
      f: {start_min: 20, end_min: 50}

  phases:
    n:
      desc: |
        Gateways have a populated in-memory route table and periodically refresh it from the orchestrator.
        User traffic is routed successfully to application backends. ZooKeeper is stable aside from low-rate quorum status logs.
        Operators run occasional direct backend probes.
      flows: [user_web_request_ok, gateway_config_refresh_ok, ops_backend_probe]
      manifestation:

    f:

        The orchestrator is mid-startup and struggles to acquire ownership locks across a large ZooKeeper namespace; gateways repeatedly attempt refreshes and get upstream errors.
        Under higher startup load, ZooKeeper session churn increases; operators attach strace and observe frequent EPIPE during writes in the orchestrator process (a Kazoo-related scaling behavior), and apply a hotfix that reduces the random churn.
        After that, ZooKeeper begins consistently rejecting oversized packets/nodes due to max buffer constraints; increasing ZooKeeper jute.maxbuffer and restarting ZooKeeper allows the orchestrator to serve routing snapshots again and gateways repopulate routes.

      events:

          at_min: 20
          component: ops_runner
          event: |
            Gateways are restarted as part of maintenance while the orchestrator is still starting; route caches are cleared and route refresh attempts begin failing, leading to 503 no_route responses with an empty route table.
          why: |
            Gateways keep routes in memory; a restart clears that state. Because the orchestrator is not yet ready to serve snapshots (still dependent on ZooKeeper startup/locks),
            refresh attempts fail and gateways reject requests with 503 no_route. This is directly observable in gateway logs; the orchestrator readiness dependency is operational knowledge.
          flows: [user_web_request_503_empty, gateway_config_refresh_fail]
          rate_multipliers:

          why: |
            Startup creates many ZooKeeper operations (ephemeral ownership locks) across a very large namespace, increasing client-side concurrency.
            The orchestrator primarily shows this as connection churn (session expired / reconnect) and prolonged startup; the specific EPIPE evidence is not normally logged, but was discovered via strace (operator-only visibility).
          flows: [gateway_config_refresh_fail]

            orchestrator.startup_waiting_locks: 2.0

              count: 1
              hosts: [opsctl-1]

              count: 1
              hosts: [opsctl-1]

            A hotfix throttles the orchestrator's ZooKeeper client startup burst, reducing random session churn; ZooKeeper then begins rejecting oversized packets/nodes due to max buffer limits, keeping route snapshots unavailable.
          why: |
            Throttling reduces client-side concurrency so random session churn drops. The orchestrator still needs to read/write large ZooKeeper nodes.
            When a node exceeds jute.maxbuffer, ZooKeeper rejects the request and closes the connection, producing consistent, repeatable failures. This is directly observable in ZooKeeper and orchestrator error logs.
          flows: [gateway_config_refresh_fail, ops_backend_probe]
          rate_multipliers:
            orchestrator.zk_session_expired: 0.6

              count: 1
              hosts: [opsctl-1]

This is directly observable via the disappearance of packet-too-large errors and the return of successful refresh and access logs, along with orchestrator metrics showing a connected zk_state.

              count: 1
              hosts: [opsctl-1]
          manifestation:

            - ops_runner.zookeeper_restart
            - orchestrator.orch_metrics_recovered

            Routes are largely repopulated and most requests are routed successfully; a small residual fraction of requests still returns 503 no_route due to partial route convergence.
