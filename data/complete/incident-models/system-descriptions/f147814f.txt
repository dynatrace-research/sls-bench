assumptions:
  - |
    Names and exact AWS resources are genericized; CloudTrail is modeled as a log-producing component rather than an AWS subsystem.
  - |
    The “mount backup disk to obtain DB password” step is represented by the attacker_db_export flow beginning once AWS abuse is underway.
  - |
    SES emailing is modeled as a small number of batch sends (500–1500 recipients per batch) to represent ~5,000 recipients without inflating per-recipient logs.
  - |
    web_frontend.http_resp_ok.dur_ms is state-scoped: normal responses stay sub-second while failure-state responses can reflect multi-second DB contention.
  - |
    web_frontend.http_resp_err.dur_ms is widened to cover end-to-end request durations that include DB lock waits up to ~30s (and overhead), avoiding impossible timing vs rds_database.db_lock_wait.waited_ms.
  - |
    Normal-phase log rate estimate: ~450 rpm * 3 logs/request ≈ 1350 logs/min, plus small background health/metrics.
  - |
    End-to-end scenario log volume estimate: ~43k logs (within 20k–100k), driven primarily by normal and degraded web request logging, with attacker and alert logs as diagnostic anchors.
