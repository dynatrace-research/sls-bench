    impbus nodes nearly simultaneously, initially halting ad serving and later restoring direct traffic first.

assumptions:
  - "Host counts are heavily downscaled: one impbus host and one gateway host represent each of six data centers; real fleet size is not modeled."
  - "Direct vs exchange traffic is represented by separate request logs and separate flow families to keep prioritization visible during recovery."
  - "The latent bug is modeled via a rare delete delta that schedules deferred reclamation; the scenario compresses the delay so the crash wave appears at failure onset."
  - "Validation is modeled as accepting the change with wait_window_s=0 and only crashing later, matching the 'eligible for distribution without waiting' condition."
  - "The near-simultaneous global crash at onset is represented by a dedicated one-shot log (impbus.crash_wave) while ongoing crash-loop behavior uses background crash/restart logs."
  - "Failure 503 response duration domain is widened (resp_503.dur_ms up to 10s) to accommodate modeled p95 latency multipliers during the outage."
  - "Partial-recovery alerting is bound to dc=AMS1 to keep the 'AMS1 restores first' storyline stable in generated logs."
  - "deploy_orchestrator.deploy_complete.duration_min is allowed to be as low as 1 minute to remain consistent with the compressed scenario timeline."
  - "Volume estimate: normal phase ~400 rpm * 3 logs/request ≈ 1200 logs/min; with similar failure traffic plus a few background/one-shot markers, total scenario is targeted around ~60k logs (within 20k–100k)."
