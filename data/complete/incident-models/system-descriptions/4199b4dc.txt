assumptions:
  - >-
    Timeline is compressed into a 60-minute scenario while preserving the causal sequence
    (AZ power loss → metadata store read-only → EC2/EBS API failures → partial power return → ELB control-plane queue storm → manual promotion restores EC2/EBS writes).
  - >-
    The model focuses on EC2/EBS control-plane read-only safety behavior and ELB control-plane backlog; RDS-specific behaviors are omitted to keep components minimal.
  - >-
    ELB task completion logs are modeled only for successful tasks because these flows also emit DNS record updates; queue backlog is represented by high task latency and queue-depth metrics, not by failed task outcomes.
  - >-
    EC2/EBS API failures in this incident are modeled specifically as read-only safety rejections (status=409 err=ReadOnlyMode) to keep per-request narratives consistent with the paired metadata-store rejection log.
  - >-
    ELB client impact is modeled as a low-rate failure flow (single-IP/non-retrying clients) rather than inflating widespread data-plane errors.
  - >-
    For path connectivity, DNS-to-ELB is modeled as a logical edge representing "DNS answer leads to a chosen endpoint connection", not a literal service-to-service call.
  - >-
    Normal-phase expected volume is approximately 790–820 logs/min (~19.8k–20.5k logs over 25 min) from ~310 rpm of combined flows plus light metrics.
  - >-
    Total expected scenario volume is approximately 55k–75k logs (within 20k–100k): failure flows are heavier and background queue/replication metrics remain visible throughout.
  - >-
    Key diagnostic visibility anchors include dc_power_az1.utility_event/rack_power_loss (trigger),
    metadata_store.leader_change and write_rejected_readonly (read-only safety),
    control_plane_api.api_response_err (customer-visible API failures),
    elb_control_plane.queue_metric and bug_scale_trigger (queue storm),
    and ebs_recovery.recovery_progress/volume_state_impaired (slow volume recovery).
