sys:
  id: dynamodb_membership_us_east
  desc: >
    A simplified model of Amazon DynamoDB in one region, focusing on how storage nodes
    periodically renew their partition membership via an internal metadata service and how
    customer API requests are routed to storage nodes. Storage nodes self-disqualify from
    serving traffic when they cannot renew membership within a deadline, which can raise
    customer error rates. The incident models a retry storm against the metadata service
    caused by larger membership payloads (driven by GSI adoption) plus a brief network
    disruption that synchronizes renewals.

states: {n: normal, f: failure}

      response per request.

    to:

        proto: grpc
        desc: Routes customer operations to storage nodes.

      Stores table partitions and serves reads/writes. Each node periodically renews its

    to:

assumptions:
  - >
    The model focuses on the DynamoDB internal membership renewal path and the retry-driven overload;
    downstream AWS services (SQS/CloudWatch/AutoScaling/Console) and the later Monday cleanup issue are omitted
    to keep one causal core with strong log observability.
  - >
    The "large membership size due to GSI adoption" is represented by larger membership_resp bytes/build_ms in failure
    and by frequent slow_membership_build markers (bytes/elapsed_ms/partitions) during timeout-prone requests.
  - >
    slow_membership_build is modeled as an in-progress warning (elapsed_ms) so it can appear before the storage node
    logs a timeout; membership_resp remains the completion-bearing log that carries build_ms.
  - >
    membership_renewal_timeout_f latency hints were adjusted so slow_build appears before the storage deadline and the
    subsequent gap to membership_timeout keeps total waited time within the membership_timeout waited_ms envelope.
  - >
    Return-path connectivity for request/response is modeled as explicit service edges (storage_node->api_frontend and
    metadata_service->storage_node) to keep flow paths traversable for log generation.
  - >
    storage_node.heartbeat eligible is state-dependent so normal heartbeats consistently show eligible=true, while failure
    allows eligible=false for disqualified nodes (aligning heartbeat semantics with the incident).
  - >
    api_frontend.access_summary err_pct is state-dependent so it can represent majority-error incident periods without
    contradicting per-request resp_err volumes.
  - >
    Failure-state metadata_service.queue_metrics and metadata_kvstore.latency_metrics ranges are widened to allow observable
    load relief after traffic is paused, while still permitting high-load values during the retry storm.
  - >
    Timeout semantics: membership_fetch_timeout waited_ms is constrained to be >= deadline_ms to avoid contradictory timeouts.
  - >
    queue_metrics queue_depth/inflight ranges were reduced to be consistent with the modeled membership request rates and
    build-time envelopes (single-digit to low-double-digit rps with ~0.1–3s builds), avoiding contradictory "thousands inflight" signals.
  - >
    Normal-phase volume estimate (15 min): ~1050 customer logs/min + ~360 membership logs/min + ~10 background logs/min
    => ~21k logs.
  - >
    Total scenario volume estimate (30 min) with failure multipliers: ~55k–65k logs (target 20k..100k),
    driven mainly by membership renewal attempts with retries during failure.
