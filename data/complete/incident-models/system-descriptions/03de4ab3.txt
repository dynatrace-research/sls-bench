sys:
  id: stackexchange_stackegg_lb_incident
  desc: >
    A multi-site Q&A web platform serves HTML pages and a lightweight game feature ("StackEgg") to logged-in users.
    Browsers connect through HAProxy load balancers to the web application tier.
    StackEgg adds an extra AJAX call for game state, increasing request rate and—because of long HTTP keep-alive—concurrent
    sessions on the load balancers. The incident models the load balancer hitting a configured concurrent-session cap,
    leading to queued TCP connects and client timeouts.

states: {n: normal, f: failure}

assumptions:
  - >
    Traffic volumes are scaled down (rpm) to keep generated log volume practical while preserving the incident mechanism
    (keep-alive driven session concurrency hitting HAProxy maxconn and causing queued connects/timeouts).
  - >
    To keep the overload mechanism quantitatively realizable with scaled rpm, HAProxy concurrency-related values are also scaled down:
    maxconn=140 represents the real-world 40k cap, and maxconn=210 represents the later raised cap (real-world ~60k). The keep-alive
    duration remains 15s because that parameter (not its absolute scale) is central to the failure.
  - >
    The maxconn value is treated as a time-consistent semantic carrier by splitting HAProxy stats/queue-warning logs into
    pre-change (maxconn=140) and post-change (maxconn=210) templates, with scenario multipliers switching which templates emit.
  - >
    To avoid "at-cap" HAProxy stats appearing before the modeled saturation transition, the initial-cap stats are split into
    a rising-load template (stats_sample_40k) and an at-cap template (stats_sample_40k_cap); the scenario switches between them.
  - >
    In HAProxy stats snapshots, cur_sess is constrained to be <= maxconn; overflow pressure is represented by queued, which can rise
    when new connects are waiting to be accepted.
  - >
    Monitoring is modeled with distinct background logs for OK vs DOWN checks in failure state; the scenario uses rate multipliers
    to avoid contradictory OK checks during the outage window while still emitting monitoring traffic.
  - >
    Normal phase log volume estimate: ~250 rpm * 4 logs/request ≈ 1000 logs/min, plus ~3–5 background logs/min across components.
  - >
    Total scenario log volume estimate (with failure multipliers): ~60k–70k logs, within the 20k–100k target.
  - >
    Key diagnostic anchors intended to be visible: haproxy_lb.stats_sample_40k then stats_sample_40k_cap then stats_sample_60k (1/min/host),
    haproxy_lb.maxconn_queue_warn_40k (activated during saturation), haproxy_lb.frontend_connect_timeout (per-failed-request),
    monitor_pingdom.check_fail during the outage window, and the feature_flag_db.flag_update / ops_puppet.puppet_change / haproxy_lb.reload_applied one-shots.
