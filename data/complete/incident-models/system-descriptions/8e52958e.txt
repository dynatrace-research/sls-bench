assumptions:
  - |
    The real incident lasted ~2h6m; this model compresses it to a shorter window while preserving the causal chain
    (power event -> reboots -> Redis down -> app boot dependency -> widespread 503).
  - |
    HAProxy backend connection retries are not modeled because the schema emits `emit` per attempt; keeping retries would make
    per-request completion logs (access logs) repeat. The incident remains diagnosable via backend_conn_fail and 503 access logs.
  - |
    Redis is modeled as a single logical cluster (cache-main) with periodic health logs and unreachable-node warnings;
    per-command Redis logs are omitted to avoid unrealistic volume.
  - |
    The main user-visible symptom (HTTP 503) is represented by HAProxy access logs and app-level 503 logs; the unicorn error page is implied by status=503.
  - |
    Normal-phase log volume estimate: ~19.2k flow logs (320 rpm * 3 logs * 20 min) plus ~150 background logs.
  - |
    Total scenario log volume estimate: ~45k–55k logs (flow-dominant; no retry amplification), staying within the 20k–100k target.
  - |
    Key diagnostic anchors intended to be visible: infra_monitor.power_glitch (one-shot), infra_monitor.host_reboot_alert (rate),
    redis_cluster.cluster_state/node_unreachable (rate), web_app.boot_fail_redis (rate), edge_lb.http_access_503 + backend_conn_fail (high-rate),
    and fleet_manager.oob_boot_error/cold_power_cycle markers during recovery pivot.
