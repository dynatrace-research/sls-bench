assumptions:
  - |
    Modeling choice: request flows start at api_app (not the edge load balancer) so that request-level retry semantics are not needed for this incident and terminal response logs remain once-per-request.
  - |
    The Pacemaker edge case is represented via repeated promote attempts failing with a colocation constraint involving a backup VIP and non-zero resource stickiness; detailed Pacemaker rule syntax is simplified.
  - |
    Pacemaker background logs are modeled as cluster-level (scope=global) streams so that after db1 is fenced/powered off the log generator does not continue emitting Pacemaker background lines "from" the offline node.
  - |
    To preserve the causal core ("backup VIP running on the synchronous replica blocks promoting it"), pacemaker.cluster_status fixes vip_backup_node=db2 in failure state; in normal it may be db2 or db3.
  - |
    Time is compressed to fit a 54-minute scenario while preserving the causal sequence (primary disk failure → failed Pacemaker promotion → operator attempts → manual promotion and app re-pointing efforts).
  - |
    The scenario ends before confirmed recovery; the incident’s headline user impact is modeled as total outage throughout the failure phase, consistent with the post-mortem summary.
  - |
    Normal-phase log volume estimate: ~650 req/min × 1 log/req ≈ 650 logs/min plus ~5–8 background logs/min (monitoring probes, Pacemaker status, DB metrics, app housekeeping, LB stats).
  - |
    Total scenario log estimate: ~50k–63k logs, dominated by request failures during the outage; key diagnostics are likely visible (Pacemaker promotion failures, app DB connect errors, monitoring alert, and operator one-shots).
