  id: filestore_control_plane

    global quota on read-only API requests. In this incident model, an internal project-management service malfunctions

    fail with 429 while mutate calls continue to succeed.

assumptions:
  - |
    The modeled "global quota" is simplified to a single global read bucket (limit 800 rpm) that can throttle all regions;
    mutate traffic uses a separate write bucket and is not throttled in this incident.
  - |
    Customer-visible impact is represented primarily by 429s on ListInstances and GetOperation; other read-only calls are omitted for compactness.
  - |
    quota_metrics is modeled as a rolling/aggregated global RPM summary that can include additional read-only RPCs not explicitly modeled
    (e.g., other list/get methods), so its observed/throttled values are kept consistent with (and not below) the modeled read-only attempt rate.
    Failure domains are tightened so throttled_rpm cannot contradict observed_rpm and stays near-total.
  - |
    internal_project_manager.sweep_cycle is treated as a periodic "cycle summary" whose api_calls roughly correspond to the internal
    ListInstances request volume. The sweep_cycle per-minute rates and api_calls domains are tuned so that implied calls/min are consistent
    with internal_project_sync_ok (20 rpm) and internal_project_sync_429 (1500 rpm) without requiring exact conservation.
  - |
    The internal project-management service is modeled as a distinct traffic source whose request volume increases sharply at failure start;
    its own logs are included as if visible to operators investigating the incident.
  - |
    Tracing is enabled and allowed to originate from the API frontend and the internal project-management service, so internal traffic can
    carry trace_ids into the Filestore API access logs.
  - |
    In the paired scenario (20 min normal, 30 min failure), normal-phase volume estimate: ~16.2k flow logs + ~0.16k background logs = ~16.36k.
  - |
    In the paired scenario, failure-phase baseline (before scenario multipliers) volume estimate: ~61.2k flow logs + ~0.60k background logs
    + a few one-shots = ~61.8k.
  - |
    Total estimated logs remain within ~20k-100k. Key diagnostics are likely visible: API 429 access logs, global quota metrics,
    synthetic check failures, internal sweep-cycle logs, and operator/alert one-shots.
