sys:
  id: qa_site_homepage_healthcheck_outage
  desc: >
    A Q&A website serves pages through a load balancer to a small pool of web frontend servers.
    The load balancer performs periodic health checks by requesting the home page ("/") and only routes
    user traffic to backends that pass. The web frontend renders the home page by formatting post snippets,
    including trimming leading/trailing Unicode whitespace from some text fields. During the incident,
    a malformed post triggers an unexpectedly expensive whitespace-trimming routine, causing home page
    requests (including health checks) to time out and the load balancer to remove all backends.

states: {n: normal, f: failure}

assumptions:
  - |
      The modeled system is a simplified Stack Overflow-like site; only the load balancer, web frontends, and monitoring are included.
  - |
      The root cause is represented as a slow whitespace-trimming step during home page rendering (web_frontend.web_trim_slow), driven by an unusually long whitespace run (~20k chars).
  - |
      web_frontend.web_trim_slow is defined as a threshold warning with elapsed time-so-far (elapsed_ms), not a completion duration, so it can occur before the LB logs an upstream timeout.
      elapsed_ms is constrained below the LB timeout envelope to avoid non-chronological timeout sequences.
  - |
      Modeled endpoints in this incident spec always return HTTP 200 on success; redirects (302) are omitted to keep LB and app completion logs consistent.
  - |
      The load balancer health check is modeled as GET / with an effective timeout around 1.5–3s; repeated failures lead to marking backends unhealthy for routing.
      Health checks are assumed to continue probing backends even when all are currently marked unhealthy, enabling recovery once a backend starts responding again.
  - |
      Request-abort logs (web_frontend.web_req_aborted) are modeled as asynchronous/background emissions during failure (and suppressed when the LB is not routing traffic),
      to avoid forcing a per-request chronology that would conflict with LB timeout logging.
  - |
      To keep pool snapshots physically coherent with 4 modeled backends, lb_pool_status now logs only healthy=N (total=4),
      and the separate lb_pool_status_all_unhealthy template represents the healthy=0/unhealthy=4 case. Scenario events suppress/enable these to match the timeline.
  - |
      Monitoring's homepage-latency alert is modeled as conditionally emitted during the initial slow-timeout phase and can be suppressed later when the LB is fast-failing 503s,
      to keep alert behavior consistent with symptom transitions.
  - |
      The deploy marker is constrained to stage=start for this incident so event narratives about "rollout starts" cannot contradict generated logs.
  - |
      Normal-phase traffic is approximated at ~720 rpm user requests plus ~24 rpm health checks; with ~2 logs per request this yields ~1488 flow-logs/min plus ~7 background logs/min.
  - |
      Total scenario log volume target remains ~48k logs over 40 minutes, within the 20k–100k requirement.
  - |
      Partial recovery is modeled as a small fraction of requests succeeding again (site_req_ok_degraded) while most still receive 503 (site_req_no_backend),
      representing an in-progress rollout before full restoration.
