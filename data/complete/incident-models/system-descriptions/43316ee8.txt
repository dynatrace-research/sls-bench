assumptions:
  - |
    Names (db1/db2, team_member_1) and exact infrastructure are simplified; the modeled system keeps the causal core:
    write spike → replication lag → risky ops → accidental data deletion → restore from older snapshot.
  - |
    Flow emission order models causality: database query/tx outcomes are logged before the Rails request completion log
    (which contains final status/duration), and paths include a logical DB→Rails return hop; the pg_primary_db1→rails_web
    edge exists to make that traversal valid.
  - |
    Backup behavior is modeled as periodic low-rate logs showing tiny/ineffective artifacts and no successful object-storage upload,
    matching “bucket empty / backups unusable” without modeling full storage infrastructure.
  - |
    Normal-phase log volume estimate: ~760 logs/min (mostly request + SQL logs) at the configured RPMs.
  - |
    Whole-scenario log volume (with the scenario timing/multipliers) is expected in the ~40k-60k range, within the 20k-100k target,
    ensuring key failure signals (lock timeouts, replication stalled alerts, ops one-shots, 503 burst) are visible.
