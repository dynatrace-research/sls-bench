sys:
  id: azure_devops_tfs_scale_unit
  desc: >
    A single Azure DevOps (TFS) scale unit serves user API traffic (e.g., Git/Build) and manages build/release agent connectivity.
    Requests enter through a regional load balancer and are processed by an Application Tier (AT) farm.
    The AT depends on an external authentication/identity service (SPS) for token/identity operations.
    During the modeled incident, a brief SPS latency spike triggers a large agent reconnect surge that saturates AT threadpool/message-queue processing and prevents health checks from completing.

states: {n: normal, f: failure}

assumptions:
  - |
    This model focuses on the Oct 4-style incident pattern: a brief SPS latency spike precipitates a prolonged AT outage via agent reconnect surges and internal threadpool/message-queue saturation.
  - |
    System repair for S8: tfs_at.mq_stats failure-state domains were widened to include near-normal lows (threads/queue_depth/batch) so early failure minutes can look only mildly impacted,
    while later minutes show higher pressure correlated with the activation of mq_starvation and probe timeouts.
  - |
    SPS periodic telemetry (sps_latency) is state-conditioned so normal baselines do not look incident-level; the decisive spike/recovery remains represented by explicit one-shot markers.
  - |
    The internal mechanism described as sync-over-async/threadpool standstill is represented operationally via rising mq_stats (threads/queue_depth) and mq_starvation warnings; logs avoid root-cause narration.
  - |
    Failure-onset baselines for probe timeouts and mq_starvation are modeled as near-zero so the scenario can activate them later via event multipliers, matching the intended progression.
  - |
    Duration domains for failure-state request logs (http_access.total_ms, agent_heartbeat.dur_ms, health_access.dur_ms) are widened up to 60s to accommodate scenario latency multipliers applied to p95 latency hints.
  - |
    The AT per-request access log reports overall duration only; dependency/queue pressure is inferred from SPS telemetry (sps_latency + spike marker) and AT mq_stats/mq_starvation plus health probe behavior.
  - |
    edge_lb.backend_state only models transitions to "unhealthy" (not "healthy") to keep the template consistent with "consecutive probe failures".
  - |
    ops_console.recycle_at is restricted to mode=single to prevent generation of "all ATs" recycle actions unless explicitly modeled.
  - |
    http_access.status is modeled as an explicit set in each state (normal: 200/401; failure: 200/503/504) to align with scenario language and downstream validators expecting enumerated status codes.
  - |
    SPS per-request logging is not modeled; instead, SPS has periodic metrics plus one-shot spike/recovery markers to keep volume realistic.
  - |
    Traffic volumes are scaled to keep total logs in 20k..100k while preserving diagnostic visibility: ~200 user rpm, ~350 agent rpm, ~100 probe rpm in normal; higher agent rpm and timeouts during failure.
  - |
    Normal-phase expected logs/min ≈ 850–900 (user 400 + agent 350 + probe 100 + background ~6), over ~20 min ≈ 17k.
  - |
    Total expected logs across the scenario ≈ 40k–60k depending on failure multipliers (agent surge and probe timeouts) and mq_starvation amplification; kept within the required envelope.
  - |
    Key visibility anchors likely to appear include: sps_auth.sps_slow_spike (one-shot), tfs_at.mq_stats (1/min/host), tfs_at.mq_starvation (activated later in failure), edge_lb.probe_timeout (activated mid-failure), and ops_console recycle/dump actions (one-shots).
