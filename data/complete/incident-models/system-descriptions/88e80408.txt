assumptions:
  - |
    The real multi-product incident is simplified to a single region with a web tier, one backend API, telemetry intake,
    node-local DNS resolvers, and a single core service-discovery/config cluster.
  - |
    The key causal mechanism preserved is: latency-tracker recycling -> missing DNS record -> NXDOMAIN not cached -> DNS
    thundering herd -> service-discovery quorum/latency problems -> widespread dependency/config lookup failures -> web/API
    intermittency.
  - |
    Web-tier DNS failures are modeled as timeouts resolving backend-api (backend-api.service.local), while the thundering
    herd root cause remains the missing latency-tracker record (latency-tracker.service.local). Separate resolver timeout
    log templates prevent contradictory qname/dep combinations in a single request chain.
  - |
    Ingestion is modeled as continuing to accept payloads (payload_ingest stays successful in failure) while latency
    tracking is often skipped; this matches “incoming data was still ingested and processed”.
  - |
    service_discovery.raft_state qps ranges are aligned to the modeled DNS/query volumes (single-digit to low-tens qps
    normal, tens qps under failure) to avoid implying large unmodeled traffic in the health snapshot.
  - |
    service_discovery.quorum_lost nodes_up is constrained to values < needed=3 (0..2) to avoid semantically impossible
    "quorum not met" emissions with 3+ nodes up.
  - |
    Normal-phase expected volume is ~1,000 logs/min (web ~540, ingest ~220, latency-tracker DNS ok ~240, plus small
    background), producing ~20k logs over 20 minutes.
  - |
    Scenario total volume is tuned to fall in 20k..100k by keeping web at ~180 rpm and concentrating the spike into DNS
    lookup flows; service_discovery.raft_state provides low-rate baseline health markers while per-request DNS logs provide
    high-visibility load signals.
