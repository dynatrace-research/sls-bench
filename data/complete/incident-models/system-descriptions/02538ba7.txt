assumptions:
  - >
    This model focuses on one brownout episode rather than all four 20-minute periods mentioned in the report; the
    memory leak is represented via elevated rss_mb/heap_mb/gc_pause_ms in mem_sample (state-dependent domains) plus periodic
    oom_panic/startup logs, not by explicitly modeling the hours-long ramp.
  - >
    Customer-visible symptoms are captured via ALB access logs with intermittent 502 (backend unreachable) and 504
    (backend processing timeout) while most ingests remain 202; failure-state flow rates are set so 502+504 are
    ~3% of ingest attempts by default.
  - >
    Blackbox probe request paths explicitly traverse the ALB and worker fleet (coarse path), while emitting only prober-side
    result logs to keep probe observability distinct from ALB access logging.
  - >
    SLO evaluation snapshot counts are sized to the modeled ingest volume (~400 requests per 60s) to avoid internal
    contradictions between SLO telemetry and request-flow traffic assumptions.
  - >
    The confusion from missing backend-side evidence is modeled by allowing the worker_telemetry_agent.http_status_report
    to be suppressed to zero during failure via scenario multipliers.
  - >
    ChatOps hypothesis notes are split into two fixed-value log templates so scenario events cannot emit a contradictory
    hypothesis marker relative to the narrative at that minute.
  - >
    Path connectivity includes an explicit ingest_worker -> aws_alb return edge so per-request logging order
    (worker completion before ALB access log) is traversable.
  - >
    Normal-phase rough volume: ~400 rpm * 2 logs/request ≈ 800 logs/min + background (~7/min) + probes (~5/min) ≈ 812/min.
  - >
    Total estimated logs over a 50-minute scenario: normal (~20k) + failure (~20k) + background/one-shots (~1k) ≈ 41k,
    within the 20k–100k target while keeping key failure signals likely visible (ALB 502/504, worker OOM restarts, SLO eval/alert).
