assumptions:
  - |-
    Names, releases, and subscription IDs are simplified; the causal core is a poison Pub/Sub welcome message causing
    an unhandled panic in a child goroutine started by the Pub/Sub client library.
  - |-
    Corologix/Sentry are not modeled as separate components; missing crash visibility is represented by Heroku Logplex
    drop/rate-limit logs plus short panic headers.
  - |-
    Heroku router success logs are modeled as response-completion logs (status/service time known), so web flows emit the app completion log first,
    then the router log; the flow path includes a coarse "return hop" back to heroku_runtime to keep the emission order traversable.
  - |-
    Dyno restarts are modeled as Heroku background dyno_start logs in failure (rather than being embedded in the poison-message flow),
    while each poison-message delivery still emits a dyno_exit marker as the terminal step of that crash-causing attempt.
  - |-
    Normal traffic volume assumption: ~500 rpm interactive HTTP (2 logs/req) plus ~60 rpm Pub/Sub messages (3 logs/msg),
    plus ~2–3 background logs/min. This yields ~1.1k–1.3k logs/min in normal.
  - |-
    Scenario log volume is intentionally dominated by Heroku router + app request completion logs to keep the incident
    diagnosable from user-facing symptoms (H10) while still showing key internal corroborators (panic header, backlog metrics, log drops, crash-loop backoff marker, operator actions).
