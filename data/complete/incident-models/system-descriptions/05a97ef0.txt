assumptions:
  - >
    The real ELB system is simplified into a single control plane, a single state store, and a data plane
    emitting access/health logs sufficient to observe: (a) logical state deletion, (b) control plane API
    degradation for existing LBs, and (c) misconfiguration of a subset of LBs after config pushes.
  - >
    "Create new load balancers works while managing existing load balancers fails" is modeled as successful
    api_create_lb flows continuing during failure while api_modify paths fail/reject.
  - >
    For config-push flows that include both control-plane and data-plane logs with the same change_id, the
    backend_count value is intended to represent the same computed/appplied backend pool size and should be
    emitted consistently within a single request flow.
  - >
    Paths include coarse "return/ack" hops (state_store->control_plane, control_plane->api, data_plane->control_plane)
    so that request lifecycles are traversable without implying the DB initiates calls.
  - >
    The db_metrics.qps field is modeled as a coarse aggregate rate over the database (including internal/non-modeled
    background queries), but is kept in the low single-digit range in normal and low double-digit range in failure
    to remain consistent with the modeled per-query DB log volume.
  - >
    The full multi-hour recovery is not modeled; the scenario ends while still failing to satisfy the
    requirement that the incident scenario ends in failure. A later successful restore/merge/re-enable is
    intentionally omitted.
  - >
    The restore tooling's waited_min is scaled to the compressed scenario timeline (minutes, not hours) so that
    restore start/fail markers can be temporally consistent in a 60-minute simulation.
  - >
    Normal-phase log volume estimate: ~570 logs/min (400 client access + ~164 API/control-plane flow logs + ~6 background),
    for ~30 minutes ≈ 17k logs.
  - >
    Total scenario log volume estimate: ~33k–42k logs across 60 minutes (client traffic dominates; control plane
    API failures and reconcile pushes provide key diagnostics), within the 20k–100k target.
  - >
    Visibility anchors: elb_state_store.audit_delete (one-shot trigger), elb_control_plane.workflow_metrics + elb_state_store.db_metrics
    (persistent degradation), elb_state_store.db_read_state_notfound + elb_control_plane.cp_state_missing + elb_api.api_modify_err_state
    (API failure), elb_data_plane.dp_config_applied_reconcile and elb_data_plane.access_err (customer-facing degradation), and
    elb_control_plane.workflow_gate_disabled plus elb_control_plane.workflow_gate_status (mitigation action and persistence).
