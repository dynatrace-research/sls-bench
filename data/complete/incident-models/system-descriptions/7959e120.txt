assumptions:
  - |-
    Names and topology are simplified from the real incident: one web tier, one messages backend, an autoscaler, a provision service,
    an internal monitoring UI, an external monitor, and a TGW-like network fabric component for observability.
  - |-
    The causal core preserved is: TGW saturation -> packet loss/RTT -> backend-call latency/timeouts -> Apache worker saturation -> increased 503s;
    autoscaling then drives a large scale-up that overloads provision-service (EMFILE + AWS throttling), delaying capacity recovery.
  - |-
    To keep traffic volumes and total log volume realistic while still modeling worker saturation, web_tier.apache_status and web_tier.worker_queue_high
    are treated as fleet-level aggregated telemetry (scope=global) rather than per-host snapshots.
  - |-
    TGW packet-per-second telemetry ranges are scaled down to match the modeled request rates (the PPS field represents only this incident-specific system slice,
    not Slack's entire real-world fleet).
  - |-
    edge_lb healthcheck summaries are split into small/large target-set log IDs so the scenario can model a later rise in registered targets during scale-out
    without forcing high target counts at failure onset.
  - |-
    Failure severity is time-varying and is primarily expressed via scenario event multipliers (early creeping errors, then a mini-peak spike, then ASG max hit,
    then partial mitigation). Failure-state value domains for web/apache and LB healthchecks are broad enough to represent both mild early degradation and later saturation.
  - |-
    Web-tier backend RPC timeout behavior is modeled as state-dependent: normal uses a ~1.5–2s deadline, while failure can extend up to ~8s under severe
    packet loss/connection stalls, keeping backend_call timeout_ms consistent with backend_timeout waited_ms and timeout-related flow latency hints.
  - |-
    Fleet size/counts are intentionally scaled down while keeping the same qualitative scaling dynamics and bottlenecks; the model retains up to 200 web host identities
    so LB target counts, autoscaler current/desired, and access-log target slots remain internally consistent.
  - |-
    Provision-service pool metrics are split by FD limit (pool_metrics_8192 vs pool_metrics_16384) so event-controlled limit changes can be represented
    without generating impossible combinations (e.g., open_files > 8192 before the restart) and without contradicting overload/FD-pressure logs.
  - |-
    Synthetic ping failures are modeled as web-tier 503 responses (web_tier.ping_respond_503) preceding the edge access log, avoiding an implausible LB-only 503
    chronology while keeping the same overall monitoring semantics.
  - |-
    Normal-phase volume estimate (20 min): ~27k–30k total logs (dominated by message_send_normal; background telemetry is intentionally modest).
  - |-
    Total scenario log estimate after rate tuning and failure multipliers: ~60k–80k logs, within the 20k–100k target.
  - |-
    Diagnostic visibility anchors expected to appear: network_fabric.packet_drop_alert + tgw_stats; web_tier.worker_queue_high + msg_send_backend_timeout;
    edge_lb.healthcheck_summary_* + a one-shot panic_mode_enabled; provision_service.pool_overload_8192/fd_exhaustion_8192 plus provision_fail_emfile/provision_fail_quota;
    autoscaler.asg_limit and instance_terminated; monitoring_ui.db_timeout/ui_request_fail; and external_monitor.page_sent.
