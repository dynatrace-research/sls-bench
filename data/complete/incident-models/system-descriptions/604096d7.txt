assumptions:
  - "Names/routes are genericized; 'bounce information' stands for rate limit/sampling/blacklist lookups described in the postmortem."
  - "The cache is modeled as in-process on API servers (no separate Redis/Memcached component); restarts implicitly clear it."
  - "Gateway logs (gw_in/gw_out) are attempt-scoped to remain coherent with retries; end-to-end client response logging is not modeled separately."
  - "The disk-usage cron is represented as a stream of write statements (disk_usage_write_stmt*) to capture DB write load without modeling an entire batch job lifecycle."
  - "The incident's 'thousands of in-flight queries' is scaled down to a few hundred in-flight refreshers to keep request rates and log volume within the 20k–100k target while preserving the same causal feedback loop."
  - "Crash-loop coherence: failure-state api_startup per_min is aligned to api_oom per_min so restarts roughly correspond to OOM crash frequency (extra non-OOM restarts are not modeled)."
  - "Autoscaler manual action log domains are constrained so {to} is always less than {from}, ensuring the minute-38 event cannot contradict itself by emitting a scale-up."
  - "Normal-phase traffic is modeled at ~172 RPM total across hit/miss; normal logs/min ≈ 140*5 + 30*7 + 2*1 ≈ 912 logs/min (+~6/min background metrics) => ~918 logs/min."
  - "Failure-phase request rates are increased vs normal to represent retry amplification and cache-cold behavior; long DB latencies (up to ~180s in api_db_query) make high in-flight counts quantitatively plausible."
  - "Scenario-sized volume target: with a 44 minute run and modeled retries, total logs are expected ~80k–90k (bounded below 100k)."
  - "Key diagnostic visibility is ensured by (a) per-minute RDS metrics, (b) frequent cache miss/refresh logs under failure, (c) gateway retry markers, and (d) API OOM/startup background logs enabled mid-incident."
