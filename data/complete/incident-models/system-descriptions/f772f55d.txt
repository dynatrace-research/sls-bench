    In this incident model, two distinct failover/election failure modes occur on the same shard: first an election bug triggered by stalled peers after a primary crash,
    then a CPU-starvation failure caused by a rollback of the election protocol interacting with a shard configuration setting.

assumptions:
  - |
    The post-mortem is simplified to a single widely-used shard (shard-07) whose write unavailability cascades into elevated API 5xx for POST writes.
  - |
    Two distinct database failure mechanisms are modeled: (1) an election fault in protocol v2 that manifests only with multiple stalled peers after a primary failure,
    and (2) CPU starvation under protocol v1 after a rollback interacts with a shard configuration setting; the protocol change itself is represented via one-shot logs.
  - |
    The “stalled nodes stopped emitting replication lag metrics but passed active checks” precursor is modeled as a low-rate repl_lag_metric_stale warning that is present before restarts and is suppressed after node restarts.
  - |
    Recovered intervals occur within the scenario’s failure phase (due to the two-phase constraint); this is made observable by switching failure-state background logs
    (normal vs degraded worker/connection snapshots) and by enabling the api_post_write_recovered_ok flow while disabling timeout flows.
  - |
    Per-request database-node internal logs are omitted to keep volume realistic; shard health is observable via background election_* and metrics logs plus router timeouts.
  - |
    Rates are scaled down to keep a single generated log file within volume targets while preserving ordering and relative behaviors.
    Normal-phase expected logs/min: ~220 rpm * ~3.05 logs/req ≈ 670 logs/min plus ~8-10 background logs/min.
    Total expected log volume over a ~60-minute scenario is ~45k-80k depending on retry intensity (within the 20k-100k target).
